# 경력기술서 리뷰 기준

- 작성일: 2026-10-12
- 기준 문서: v.2.1
- 사용처: resume-reviewer (단독 첨삭, 자동 검수, 공고 맞춤 리뷰)

v.2.1을 읽고 섹션마다 하는 역할과 형식을 파악한 뒤, 그 성격에 맞춰 기준을 정했다. 기준을 처음 만들 때 실제로 걸린 사례와 "알려진 사실"은 개인정보라서 `private/examples.md`에 따로 둔다 (git에 올라가지 않는다). 리뷰할 때는 두 문서를 함께 읽고, 그 사례를 판단 기준점으로 쓴다.

## 섹션 간 관계

```
헤더 헤드라인 (주장)
  └▶ Introduce (주장을 풀어 씀)
       └▶ Career (책임 범위 요약)
            └▶ Work Experience (상세 사례 = 근거)
       └▶ Activity / OpenSource Contribute (공유·학습 태도의 근거)
  Personal Project (경력 밖 기술 역량)
  Education (기본 정보)
```

위쪽 섹션의 주장마다 아래쪽 섹션에 근거가 있어야 한다. 근거 없는 주장은 섹션과 상관없이 심각도 높음으로 본다.

## 심각도

| 심각도 | 기준 |
|---|---|
| 높음 | 읽는 사람이 사실을 의심하거나 오해할 수 있다. 근거 없는 주장, 기준점 없는 수치, 제목과 맞지 않는 본문, 불분명한 기여 범위 |
| 중간 | 설득력이 떨어진다. 유형별 필수 요소 누락, 추상적 표현, 섹션 사이 중복, 오래된 항목 |
| 낮음 | 완성도 문제다. 오타·띄어쓰기, 날짜·서식·문체 불일치 |

## 지킬 것

제안이 아래 강점을 깨면 안 된다. 다른 항목을 고칠 때도 이 수준을 목표로 삼는다.

| 강점 | 설명 |
|---|---|
| 문제→해결→성과 구조 | 문제(지표) → 분석 → 해결 → 결과 수치가 한 흐름으로 이어진다 |
| 개선 전후 수치 | 비율과 함께 개선 전후 값을 적는다 |
| 구체적인 기술 디테일 | 기법·API 이름을 그대로 적는다. 일반적인 표현으로 뭉개지 않는다 |
| 근거 링크 | 기사, 블로그 글, 발표 자료, PR |
| 팀 규모·기여도 표기 | 팀 인원과 기여도, 기여도를 잰 기준 |

## 공통 기준

| 기준 | 확인 방법 |
|---|---|
| 섹션별 문체 | Introduce는 합니다체, 나머지 섹션은 명사형 종결. 섹션 안에서 문체가 섞이지 않는다 |
| 수치 신뢰성 | 수치마다 기준점(개선 전후 값이나 모수)과 측정 대상이 있는가. 해석이 애매하거나 비현실적인 수치는 심각도 높음 |
| 모호·과장 표현 | 금지어: 극대화, 최대화, 무한한, 풍부하게, 많은, 노력, 참여, 담당, 단독으로 쓴 "기여". 구체적인 행동과 결과로 바꾼다 |
| 제목-본문 일치 | 항목 제목의 키워드가 본문에서 설명되는가 |
| 최신성 | "진행 중" 항목이 아직 사실인가, 리뷰하는 날 기준으로 오래된 항목이 있는가 |
| 표기 통일 | 날짜는 `YYYY.MM`, 기간은 `YYYY.MM ~ YYYY.MM`, 링크 텍스트 형식, 같은 레벨 항목의 제목 서식 |
| 맞춤법·띄어쓰기 | 붙여 써야 할 말, 쉼표 뒤 공백, 제목 끝 공백 |

## 섹션별 기준

### 헤더

- 성격: 첫인상이자 외부 증거(GitHub, 블로그, 발표)로 가는 입구다.
- 형식: 이름, 헤드라인 1줄, 링크(GitHub, LinkedIn, Tech Blog, Speaker Deck), 연락처
- 기준
  - 헤드라인의 주장을 본문의 어느 항목이 뒷받침하는지 짚을 수 있는가
  - 링크가 살아 있고 표기 형식이 하나로 맞는가

### Introduce

- 성격: 합니다체로 쓴 서술형 자기소개다. 성과 목록이 아니므로 bullet이나 수치를 억지로 요구하지 않는다.
- 형식: 3문단, 문단마다 주제 하나 (① 도메인·기술 ② 일하는 방식 ③ 협업)
- 기준
  - 문단 하나에 주제 하나인가, 문단당 2~3문장인가
  - 문장마다 아래 섹션에 근거가 있는가. 예: "문서화해 공유" → 블로그·발표, 안정성 지표 → Career
  - 비유나 추상적인 문장은 구체적인 행동이 함께 있을 때만 남긴다

### Career

- 성격: 회사별 책임 범위를 한눈에 보여 주는 요약이다. 자세한 내용은 Work Experience가 맡는다.
- 형식: 회사, 기간(총 기간), 조직 | 직무 (팀 인원), 서비스명과 링크, 명사형 종결 bullet
- 기준
  - 회사마다 위 필드가 빠짐없이 있는가
  - bullet은 한 줄이고 "무엇을 + 결과 키워드" 형태인가
  - bullet마다 대응하는 Work Experience 항목이 있고, 거기 없는 성과를 주장하지 않는가
  - 인원이 적은 팀이면 내 역할 범위(리드, 단독, 공동)가 보이는가
  - 기간이 겹치거나 비는 곳이 없는가. 공백은 "알려진 사실"을 확인한 뒤 판단한다

### Work Experience

- 성격: Career 요약을 뒷받침하는 상세 사례 모음이다. 이력서의 핵심 섹션이다.
- 형식: 왼쪽 열은 회사명, 오른쪽 열은 항목들. 항목마다 굵은 제목과 `-` bullet이 있고, 하위 bullet이나 날짜별 하위 항목이 붙기도 한다.
- 기준: 항목의 유형을 먼저 분류하고, 유형별 필수 요소가 있는지 본다.

| 유형 | 판별 | 필수 요소 |
|---|---|---|
| 기능 개발·런칭형 | 비즈니스 요구로 새 기능이나 서비스를 만들었다 | 기능 범위, 내 역할, 런칭 결과(일정, 사용자, 안정화 지표) |
| 문제 해결형 | 지표나 불편으로 드러난 문제를 해결했다 | 문제(지표) → 원인 분석 → 해결 → 개선 전후 수치 |
| 기술 심화형 | 특정 기술을 깊게 적용하거나 도입했다 | 상황·제약 → 기법과 고른 이유 → 효과(측정 대상을 밝힌다) |
| 정책 대응형 | 외부 정책이나 OS 변경에 대응했다 | 변경점 → 앱 영향 → 대응 → 결과(기한 안 배포, 이슈 0건 등) |

- 모든 유형에 공통으로 보는 것
  - 제목은 명사형이고 본문과 맞는가
  - 제안했는지, 주도했는지, 공동 작업인지 드러나는가
  - 항목당 bullet은 3~5개인가
  - 비즈니스 임팩트가 큰 항목이 앞에 오는가
  - 성격이 다른 작업이 한 항목에 섞여 있지 않은가
- 정량 성과를 내기 어려우면 대체 지표를 제안한다. 작업 시간, QA 리드타임, 크래시·ANR, 연결 성공률, 마이그레이션 범위(파일·모듈 수) 등이다.

### Personal Project

- 성격: 경력 밖에서 보여 주는 기술 역량의 증거다.
- 형식: 프로젝트명(영문명), 기간, 형태(개인/팀), Github 링크, 한 줄 소개, 팀 정보, 기술 성과 bullet 2~4개
- 기준
  - 경력에서 보여 주지 못한 역량(기술, 역할, 도메인)을 보여 주는가
  - 팀 프로젝트라면 인원과 기여도, 기여도를 잰 기준이 있는가
  - 수치에 기준점이 있는가 (공통 기준보다 엄격하게 본다)
  - 경력에 비해 오래된 항목이면 유지, 축약, 삭제 중 무엇이 맞는가

### Activity

- 성격: 커뮤니티 활동과 지식 공유의 근거다. Introduce의 "공유하는 습관"을 뒷받침한다.
- 형식: 단체명과 기간, 역할·산출물 bullet
- 기준
  - 역할(발표자, 강사, 운영진)과 산출물 링크가 짝지어 있는가
  - "진행 중"이 아직 사실인가
  - 단체 설명 줄을 넣을지 여부가 단체마다 같은가
  - 최신순인가

### OpenSource Contribute

- 성격: 외부 프로젝트에 코드로 기여한 증거다.
- 형식: 저장소명, Github·PR 링크, 프로젝트 소개, 기여 내용
- 기준
  - PR 링크와 머지 여부가 있는가
  - 문서 기여인지 기능 기여인지 드러나는가
  - 항목 서식이 서로 같은가
  - 기여가 작으면 묶거나 줄이는 안을 제안한다

### Education

- 성격: 기본 정보
- 기준: 학교, 기간, 학과, 학위가 있는가. 형식만 확인한다.

### 전체

- 분량, 섹션 사이 중복, 오래되었거나 약한 항목
- 첫 30초(헤더, Introduce, Career)만 읽어도 연차, 도메인, 대표 성과가 잡히는가

## 알려진 사실

리뷰하기 전에 `private/examples.md`의 "알려진 사실" 표를 확인한다. 이미 확인된 사실은 다시 묻지 않고, 지적 대신 대응 방안을 제안한다.

## 제안 작성 규칙

- 없는 수치나 사실을 지어내지 않는다. 필요한 값은 `[확인 필요: 측정 전 값]`처럼 비워 두고 "확인 필요" 목록에 올린다.
- "현재" 칸에는 문서의 원문을 그대로 옮긴다. 그래야 resume-update가 위치를 찾을 수 있다.
- 같은 문제가 여러 곳에 있으면 한 제안으로 묶고 위치를 모두 적는다.

## 출력 형식

```markdown
## 리뷰 요약 (v.X.Y 기준, YYYY-MM-DD)
전체 인상: ...
지킬 강점: ...

## Work Experience 체크
| 항목 | 유형 | 필수 요소 | 기여 범위 |
|------|-----|---------|---------|
| {항목 제목} | 문제 해결형 | 문제 O / 원인 O / 해결 O / 수치 O | △ |
| {항목 제목} | 정책 대응형 | 변경점 O / 영향 O / 대응 O / 결과 X | △ |

## 제안
| # | 섹션 | 심각도 | 현재 | 제안 | 버전 영향 |
|---|------|------|------|------|----------|
| 1 | Personal Project > {프로젝트명} | 높음 | "정확도 N% 개선" | "{측정 대상} 정확도 [확인 필요: 이전 값]% → N%" | patch |
| 2 | Introduce | 중간 | ... | ... | major (재작성) |

## 확인 필요
- 1번: 정확도의 개선 전 값과 측정 방식
```

- resume-update는 "버전 영향" 열을 보고 반영할 버전을 정한다.
- "확인 필요" 항목은 사용자가 답하기 전에는 반영하지 않는다.
